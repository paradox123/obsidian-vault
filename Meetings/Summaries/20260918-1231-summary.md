# Care API Stabilisierung und CareCache-Test

## Summary

- Richard und Daniel arbeiteten an einem lokalen Testlauf der Care API auf dem Branch `feature/care-api-java-stabilization` sowie an der Anbindung an die lokale NCG-/CareCache-Umgebung.
- Die Care API wurde lokal im Read-only-Modus betrieben und über Port `8091` angesprochen. Einzelne direkte API-Aufrufe über Bruno/Postman funktionierten, teils aber mit langen Laufzeiten von ca. 21 Sekunden bzw. später ca. 5 Sekunden.
- Beim Triggern des `CareCustomerSyncJob` über das Job Dashboard/CareCache traten zunächst Auth-/Token-Probleme auf: Die lokale Umgebung versuchte gegen `securitydev.auto-nagel-cloud.de` bzw. `dev.auto-nagel-cloud.de/shop/security` zu validieren und brach mit `issuer name does not match authority` sowie HTTP 500 ab. ![AuthServer token endpoint error](Attachments/20260918-124954-489-001827-cropped.png)
- Zur lokalen Fehlersuche wurden Authentication/Authorization in mehreren Services bzw. Middleware-Pipelines testweise deaktiviert bzw. umgangen; danach konnten einige Job-/Status-Endpunkte lokal antworten, während andere nicht gestartete Services weiter `Connection refused` lieferten.
- Zur Last-/Integrationserprobung wurden mehrere CARE-Endpunkte per `curl` gegen `localhost:8091` parallel aufgerufen, u. a. `statistics/vehicle-identifications`, `statistics/kpi`, `customers/checksums` und `customers/marketing`. Die Antworten enthielten teilweise Service-Fehler wie `CARE_CUSTOMER_UNAVAILABLE` und `CARE_REPORTING_UNAVAILABLE`. ![CARE unavailable responses](Attachments/20260918-132151-223-005024-cropped.png)
- In der Java-Care-API fiel eine Validierungs-/Datenfrage auf: Im Marketing-Customer-Flow wird bei `customer.getVehicle() == null` aktuell eine `CustomerReadException(500, null)` geworfen. Es ist unklar, ob solche Datensätze verworfen/als Fehler gemeldet oder trotz fehlendem Fahrzeug weitergegeben werden sollen.
- Daniel wies darauf hin, dass die CARE-Daten teils sehr schlecht strukturiert sind und viele Freitextfelder enthalten; Richard braucht deshalb reale, anonymisierte Beispieldaten, um die Validierung praxisnah einstellen zu können.
- Hinweis aus dem Screensharing: In Konfigurations-/Scratch-Dateien waren Zugangsdaten bzw. API-/Basic-Auth-Secrets sichtbar. Wenn Aufzeichnung oder Screenshots über den vertrauten Kreis hinaus geteilt werden, sollten diese Secrets als kompromittiert betrachtet werden.

## Decisions

- Die bestehende produktive/Server-Care wurde nicht ersetzt; getestet wurde lokal gegen die live CARE-Datenbank bzw. interne CARE-Endpunkte.
- Für die weitere Stabilisierung soll nicht nur mit künstlichen Beispieldaten gearbeitet werden; Richard soll einen anonymisierten Auszug echter CARE-Daten erhalten.
- Für den Export reichen zunächst ungefähr die ersten 5.000 Datensätze bzw. ein ausreichend repräsentativer Teilbestand, nicht zwingend ein kompletter Dump.
- Die lokalen Auth-Workarounds waren reine Debug-/Testmaßnahmen, keine abschließend beschlossene Produktivlösung.

## Open Questions

- Wie streng darf die Care API validieren, bevor sie Daten verwirft oder Fehler zurückgibt?
- Welche fehlerhaften CARE-Daten müssen durch die Care API toleriert und an CareCache weitergereicht werden, weil CareCache sie später bereinigt?
- Wie soll die API reagieren, wenn bei einem Marketing-Customer-Datensatz `vehicle == null` ist: Fehler, leerer Teildatensatz oder Weitergabe mit fehlendem Fahrzeug?
- Warum liefern die Marketing-/Checksum-/KPI-Aufrufe in der lokalen Testkonstellation `CARE_CUSTOMER_UNAVAILABLE` bzw. `CARE_REPORTING_UNAVAILABLE`?
- Welche Auth-/Security-Konfiguration ist für lokale Integrationstests vorgesehen, ohne global Authentication/Authorization auskommentieren zu müssen?
